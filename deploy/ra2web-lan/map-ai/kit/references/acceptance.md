# 地图怎么验收

每次验收绑定最终 `.map` 的 SHA256、客户端构建、MOD/规则、浏览器及设备。地图发生变化后更新报告；未执行的项目保留 `pending`，失败记录 `fail` 和复现步骤。

## 第一层：文件与独立数据解码

执行：

```sh
node scripts/validate.mjs 最终地图.map --design design.json --report static-report.json
node scripts/preview.mjs 最终地图.map --out preview.svg
```

要求退出码 0、`staticPassed=true`、`nativeDecoded=true`，并核对预览与设计意图。报告仍为 `static-pass-runtime-pending`。

脚本检查完整压缩地块、对应的覆盖物图层、瓦片/对象白名单、N 个真实出生点、2 MiB 限制、未编辑字节往返，以及原始读取器交叉解码。还会给出基地净空、近矿数量和地面通道的有限近似结果。此层不执行游戏模拟，也不验证岸线美术或经济平衡。

## 第二层：编辑器和房间

1. 在 `https://ra.winlife.fun/map-editor/` 导入最终 `.map`。确认名称、剧场、人数、矿区、油井和每个出生点；保存数据预览及实际界面截图。
2. 不编辑地导出一份地图，再运行校验器。核对文件 SHA；如工具改写了字节，保留两个文件并比较语义，不沿用旧文件的运行证据。
3. 点击“加入我的游戏”，刷新游戏，在自订地图中按名称选中。等地图预览完成再点击使用，防止把上一张图误当成已选中的图。
4. 核对实际可用人数、出生点编号和观察者位置。9–16 人需使用包含人数扩展的客户端。
5. 非房主在自己的行选择国家、颜色、出生点和队伍，房主端看到相同值。已点“接受”的玩家先点“未准备就绪”再改；开启“房主队伍”时位置/队伍由房主控制。

## 第三层：实际单机开局

至少执行一局 `1 真人 + N-1 AI` 的加载与运行测试。对每个出生点分别验证或取得清楚的观察证据；没有覆盖的位置写明未验证。

| 项目 | 需要实际看到的结果 |
| --- | --- |
| 全部出生点 | 单位出现在对应位置，没有重叠、落水、悬空或不可玩边缘 |
| 基地建设 | MCV 能展开；电厂和矿厂能实际放置；有后续建设空间 |
| 资源 | 矿车能到达矿区并带回资源，没有卡在岸边、树或建筑后 |
| 通路 | 地面单位能走完设计中的每条主要路线；多单位会车与狭口转弯可用 |
| AI | AI 能展开、采矿、生产并进攻；没有长时间困在出生地 |
| 视觉 | 无缺图、破碎岸线、错误高度、桥梁或遮挡；SVG 正确不代替此项 |
| 负载 | 记录设备、浏览器、分辨率、单位规模及实测帧率/帧耗时，与同设备基准图比较 |
| 退出 | 能正常退出或完成胜负流程，不遗留测试房间 |

不要把“升高几个地块”视为已经生成坡道，也不要把两块画面相邻的陆地视为坦克一定能通行。油井的实际占领、收入和阵营差异属于运行验证。

## 第四层：真正的联机传图与同步

使用两个独立浏览器配置或设备、两个不同昵称。客机应没有预存这张自制地图，避免用共享缓存冒充传图成功。房主导入最终文件并建房，客机加入、接受，双方实际开局。

- 记录房主的导入文件及 SHA，客机收到地图并完成加载的证据。仅看到同名地图不能证明字节相同。
- 双方操作基地、生产单位、采矿和移动；建议按目标人数加入 AI 并运行至少 10 分钟。两台浏览器在同一台电脑运行需要如实注明，不能声称是多台实体设备压测。
- 读取 `/healthz` 的目标 `games[]`：`started=true`，网络轮次持续前进，`desynced=false`，`hashes[].values` 中双方在同一个轮次的校验值相等。RTT 很低不证明模拟同步。
- 可使用附带的只读采集器保存真实接口数据：

```sh
node scripts/collect-network.mjs --base https://ra.winlife.fun --host AIHost --guest AIGuest --map 最终地图.map --out evidence/network.json --seconds 600
```

先开局再运行。采集器只保存目标对局，要求两个昵称不同、轮次前进、无不同步及至少三个不同轮次的双方一致校验值。`/healthz` 不提供地图 SHA，因此采集器记录的文件 SHA 来自操作者，仍需另附浏览器导入/传图证据。接口不可用、双方校验值缺失或不能确认地图绑定时，相关项目保留待测。

## 记录与交付

`runtime-acceptance.json` 的每项初始为：

```json
{"status":"pending","evidence":[],"notes":""}
```

执行后填写实际 `pass/fail/pending` 与观察。证据使用交付目录中的相对路径，例如：

```json
{"status":"pass","notes":"客机选中国、蓝色、3号位置、B队，房主显示一致。",
 "evidence":[{"path":"evidence/guest-room.png","sha256":"证据文件的真实SHA256"}]}
```

记录 `testedClient` 和 `testedMod`。使用以下命令检查记录完整性、文件散列及网络结果：

```sh
node scripts/check-evidence.mjs 最终地图.map runtime-acceptance.json
```

退出码 2 表示仍有待测或证据缺失，退出码 1 表示文件/命令错误。`evidence-complete` 只表示记录及其附件完整；此脚本不会判断截图是否真实，也不会替执行者确认游戏平衡。实际结论必须来自真实运行观察。

最终交付说明区分：静态检查、原生数据解码、实际单机测试、联机测试及未覆盖项。不要把服务器协议假客户端测试当作实际引擎开局，不用旧图或另一个文件的截图替代当前版本。
